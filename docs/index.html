SpecLane: Serving Small Hybrid-Attention Models Under Agent Traffic

How should an inference engine be configured to serve small language models to AI agents? I study two open-weight models, Qwen3.8-27B-FP8 and Qwen3.5-9B, running on the vLLM engine. I start from the default setup, change one setting at a time, and measure speed, responsiveness and answer quality.

vLLM 0.33.0 · one NVIDIA H100 and one L40S GPU on cloud instances · one run per measurement · code and raw results are in the repository

In short

  • What this is. A measurement study of features that already exist in vLLM. It does not propose a new method.
  • Main finding. Speculative decoding, using the multi-token-prediction (MTP) head that ships with each model, made text generation 50–124% faster on the 27B model and up to 77% faster on the 9B model. I measured no loss in answer quality.
  • A setting I do not recommend. Storing the attention cache in 8-bit floating point (FP8) made generation slower and the first response later at this model scale, so I do not recommend it.
  • A startup problem. With default settings, vLLM 0.33.0 cannot start the 27B model on a single H100 GPU, because its default limit on concurrent sequences is higher than the memory for per-sequence state can support.
  • Agent harness study. I also evaluated a prompt-based agent harness on two agent benchmarks. At the sample sizes run, it showed no measurable accuracy difference, so I report it for completeness and draw no conclusion from it.

Key terms

Throughput

How many output tokens (word pieces) the server generates per second, summed over all requests. Higher is better.

Time to first token (TTFT)

How long a request waits before the first token appears. It governs how responsive the system feels. Lower is better.

p99

The 99th percentile: the value that all but the slowest 1% of requests stay under. With 24 requests per measurement, it is simply the slowest request.

Concurrency (c)

How many requests are in flight at the same time. c = 1 measures a single user; c = 16 measures a loaded server.

Multi-token prediction (MTP)

Alongside its normal output layer, each model carries a small extra head trained to predict several upcoming tokens at once. In speculative decoding that head proposes the next few tokens cheaply, and the full model verifies all of them in a single pass, keeping every correct proposal. The number after MTP in the detailed tables is how many tokens are proposed per step.

KV cache

Memory that stores the attention keys and values of earlier tokens so they are not recomputed. “FP8 KV cache” stores them in 8-bit precision to save memory.

Why 3 on one model and 2 on the other?The number is how many tokens the MTP head proposes per step. Proposing more can save more work when the proposals are right, but each wrong proposal is wasted effort, so every model has a best value. I used 3 on the 27B, the value recommended for that model, and tried 1 and 2 on the 9B: 2 was faster (+77% against +44% at c = 1), and it is also the value in that model’s documentation. I did not search other values on the 27B, so 3 there is the recommended setting rather than a tuned optimum.
Read speed and responsiveness together.A faster server can still have a slower worst case. On the 27B model with 16 requests at once (shared_prefix workload), MTP-3 raised throughput by 75% but also raised the p99 time to first token from 0.53 s to 0.79 s. The FP8 KV cache raised it to 1.47 s while also lowering throughput, so it was worse on both measures.

Answer quality

In principle, speculative decoding does not change what the model outputs, because every proposed token is verified by the full model. An implementation can still differ from the theory, so I checked. I deployed the default and the MTP setup of each model as live servers and asked both the same 200 grade-school math questions (a fixed random sample of GSM8K), with the sampling temperature set to 0 and the model's extended “thinking” mode turned off. An answer counts as correct only if its final number exactly matches the reference.

Method

Models and hardware

Qwen3.8-27B-FP8 (a 27-billion-parameter model, 31 GB, Apache-2.0 licence) on one H100 GPU with 80 GB of memory, and Qwen3.5-9B (9 billion parameters, 19 GB, Apache-2.0) on one L40S GPU with 48 GB. Each model runs on its own GPU in a separate container. Software: vLLM 0.33.0, PyTorch 2.14, CUDA 13.0.

The baseline

The engine's default settings, plus only what is needed to start the model and a fixed context length of 16,384 tokens. The 9B model needs --trust-remote-code. The 27B model needs --max-num-seqs 512 (explained below).

Settings tested

Each test changes exactly one setting from the baseline: speculative decoding with k proposed tokens, the FP8 KV cache, scheduler limits, asynchronous scheduling, or turning prefix caching off. I then combine the best ones.

Workloads

shared_prefix: a 3,000-token system prompt shared by all requests, a 150-token question, and up to 256 output tokens. agent_sessions: six-turn conversations with a 2,000-token shared system prompt, where each turn resends the full history. Prompts are random words, so no request is answered from cache by accident.

The load generator runs inside the same container as the server, so no network delay is included. Every measurement is preceded by warm-up requests drawn with a different random seed. I test 1 and 16 concurrent requests. shared_prefix sends 24 requests per measurement. agent_sessions sends 24 requests at c = 1 and 96 at c = 16. Throughput is the number of output tokens divided by the elapsed time.

A startup failure on a hybrid-attention model

Qwen3.8-27B uses a cheaper “linear” form of attention in 48 of its 64 layers. Those layers keep a fixed-size state for every active sequence, so the number of sequences an engine can hold is limited by that state as well as by the KV cache. With vLLM 0.33.0’s default settings on one H100, the 27B model failed to start. The engine stopped while preparing its optimised execution graphs, with this error:

ValueError: max_num_seqs (1024) exceeds available Mamba cache blocks (745).
Each decode sequence requires one Mamba cache block, so CUDA graph capture
cannot proceed. Please lower max_num_seqs to at most 745 or increase
gpu_memory_utilization.

The default limit of 1,024 concurrent sequences is higher than the 745 state slots that fit in memory next to the model. Setting --max-num-seqs 512 fixes it, so I include it in the baseline. In this report, “baseline” therefore means the defaults plus whatever is needed to start.

More findings

The FP8 KV cache: not recommended at this scale

Storing the KV cache in 8-bit precision lowered throughput (by 14% on the 27B model with 16 requests at once) and raised the p99 time to first token from 0.53 s to 1.47 s on shared_prefix. Its purpose is to free memory, but at these model sizes memory is not the limiting factor, and the extra conversion work shows up as lost speed. It is not part of the recommended setup.

Agent harness study

I also asked whether a carefully engineered prompt for the coding agent (the “harness”), combined with the tuned engine, makes agents more accurate. I compared it with the default agent on the default engine, using Terminal-Bench 2.1 (command-line tasks, Qwen3.8-27B) and τ²-bench (customer-service conversations, Qwen3.5-9B). At the sample sizes I could afford, there was no reliable difference.

A larger, repeated study is the natural next step for any agent-accuracy claim.

Evaluation pipeline fixes

  • Missing tool-calling settings. My first Terminal-Bench pilot scored 0 on every task because the server rejected the agent’s tool definitions with an HTTP 400 error, so no tokens were ever generated. I withdrew that pilot and enabled tool calling on every server.
  • τ²-bench judge defaults to OpenAI. Some τ²-bench tasks are graded by a language model. By default it calls an OpenAI model, which failed without a key and scored the task 0 in both arms. The grader now uses my default 27B server in every run.
  • Sandbox image builds. The older container-image builder failed on plain Ubuntu task images (python: not found); selecting its newer version fixed it. Later sandbox conflict errors came from starting 30 sandboxes at once. Those trials are excluded and are not counted as model failures.

Reproduce

Everything is driven by a small, engine-agnostic configuration layer: a model registry, a set of named serving profiles (the baseline and one-change variants), a workload generator, a load-testing client and a quality check. Any machine with a supported GPU and vLLM can run it. The repository README lists the exact commands for each step:

  1. Stage the model weights and verify that every candidate setting is accepted by the installed vLLM version.
  2. Sweep the profiles and workloads at the chosen concurrency levels, with the accuracy check enabled.
  3. Serve the baseline or the tuned (MTP) profile behind an authenticated, OpenAI-compatible endpoint.
  4. Rebuild the tables, figure and paper directly from the raw result files with paper/make_results.py.

A deployed endpoint keeps its GPU allocated until it is stopped, so shut it down when a run is finished.

Appendix: how multi-token prediction works

What I did and did not do.I did not design or train the MTP head. It ships inside each Qwen model, trained by the model’s authors. My work is to switch it on, choose how many tokens it proposes, and measure the result. This section gives the mathematics of how it is used and why it makes generation faster, and checks the theory against my measurements.

1. The head proposes, the model verifies

Plain decoding runs the full model once per generated token. Speculative decoding adds a cheap proposer that guesses the next k tokens; the full model then checks all k guesses in a single forward pass. With MTP, the proposer is a small head attached to the model. In the general MTP design (published for DeepSeek-V3; I have not inspected the exact Qwen layer layout), the head for the j-th future token combines the model’s hidden state with the embedding of the token just proposed, passes them through one light transformer block, and reuses the model’s own output layer:

h′j = Blockj( Wj [ norm(hj−1) ; norm(E(x̂j−1)) ] )
qj = softmax( LMhead( norm(h′j) ) ),   x̂j = argmax qjproposal j = 1…k; E and LMhead are shared with the main model, so the head is small

The model authors train the head with an extra loss for each future position, added to the usual next-token loss, where λ weights the extra terms:

L = Lmain + λ · Σj=1..k Lj,   Lj = − log qj( xt+j+1 | x≤t )training objective (done by the model authors, not by me)

2. Verification keeps the output identical

Let p be the full model’s distribution at a position and q the proposer’s. A proposed token x is accepted with probability min(1, p(x)/q(x)). At the first rejection, the token is replaced by a sample from the leftover distribution, and the remaining proposals are discarded:

P(accept x) = min(1, p(x)/q(x))    on reject: x ∼ norm( max(0, p − q) )at temperature 0 this reduces to: accept if x̂ = argmax p, otherwise take argmax p

The emitted token then follows exactly p, the full model’s own distribution:

P(x) = q(x)·min(1, p(x)/q(x)) + [ 1 − Σy min(p(y), q(y)) ] · max(0, p(x) − q(x)) / Σy max(0, p(y) − q(y)) = p(x)the first term is min(p,q); the second is the leftover mass, which supplies exactly p − min(p,q)

So speculative decoding changes the speed, not the distribution of outputs. If all k proposals are accepted, the same verification pass also yields one extra token for free, so a step produces between 1 and k+1 tokens.

3. Expected tokens per step and the speedup

Let α be the probability that a proposal is accepted, assumed equal at every position. A step produces j tokens when the first j−1 proposals are accepted and the next is not, so the expected number of tokens per step is a geometric sum. Let c be the cost of one proposal step relative to one full-model step. Because verifying k+1 positions costs about one full-model step when decoding is limited by memory bandwidth, the speedup is:

E[tokens per step] = Σj=0..k αj = (1 − αk+1) / (1 − α)
Speedup S(k) = E[tokens per step] / (1 + c·k)upper limit as k grows: 1 / (1 − α)

Two forces set the best k. Each extra proposal adds a term αk to the numerator, which shrinks geometrically, while it adds c to the denominator. The speedup therefore rises, peaks and then falls. For illustration, with α = 0.6 and c = 0.1, S(1) = 1.46, S(2) = 1.63, S(3) = 1.67, S(4) = 1.65 and S(6) = 1.52, so the best value is 3. This is a worked example of the shape, not a measurement. It is why each model has a best k and why I compared 1 and 2 on the 9B.

4. Checking the theory against my measurements

My measured speedups bound the acceptance rate. Since S = E / (1 + c·k) ≤ E, setting E equal to the measured speedup and solving for α gives a lower bound on the acceptance rate. This assumes equal acceptance at every position, which is an approximation.

Measured speedups come from the agent_sessions workload. Two observations are consistent with the model. First, the speedup is below the cap of k+1 in every row, as it must be. Second, the speedup is smaller with 16 requests at once than with one. Batching makes the full-model step more compute-bound, so verifying extra tokens costs more and the effective c rises. I did not measure α or c directly, so this explanation is a consistent reading of the numbers and not a tested claim.
